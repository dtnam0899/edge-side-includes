# services/core-backend (.NET)

<!-- Supplements the repository root CLAUDE.md for this project. Keep only verified facts. -->

## Overview
Core API, domain logic and auth for ESI; consumed by `web/esi-portal` (including its AI assistant module) and `services/ai-agents`.

## Stack
- .NET 10 (LTS, supported to 2028-11-14), ASP.NET Core (ADR-0001). SDK pinned in `global.json` (10.0.402, runtime 10.0.13). Identity provider: Auth0 through standard OIDC/JWT (ADR-0006, `Microsoft.AspNetCore.Authentication.JwtBearer` 10.0.13; no provider SDK).
- Data store: PostgreSQL for the app's own data (ADR-0008; EF Core 10.0.13 with `Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.3 and migrations). Users' target databases are SQL Server only, through `Microsoft.Data.SqlClient` 6.1.7 (pinned directly).
- Libraries decided by ADR: `Microsoft.SqlServer.TransactSql.ScriptDom` for SQL validation (ADR-0004), `System.Security.Cryptography.AesGcm` for envelope encryption (ADR-0003). Core also validates DSL itself when saving (ADR-0002).
- Packages: versions only in `Directory.Packages.props` (central management with transitive pinning); `packages.lock.json` per project, restored with `--locked-mode` in Docker.
- Tests: xUnit v3 on Microsoft.Testing.Platform (`global.json` `test.runner`), so `dotnet test` takes `--project <path>`.

## Commands (run from this directory)
- Restore/build: `dotnet build` (needs the .NET 10 SDK; otherwise use the Docker commands)
- Unit tests: `dotnet test --project tests/Esi.Core.UnitTests`
- Format check: `dotnet format --verify-no-changes --exclude src/Esi.Core.Infrastructure/Persistence/Migrations`
- Run: `dotnet run --project src/Esi.Core.Api` (set `ESI_CORE_AppDb__ConnectionString`, the master key variables and either `ESI_CORE_Auth__Mode=LocalAdmin` with `ASPNETCORE_ENVIRONMENT=Development` or the Oidc settings first; compose sets local values)
- Refresh published inputs after bumping `published-packages.json`: `NODE_AUTH_TOKEN=$(gh auth token) scripts/sync-published.sh` (Docker; downloads `@dtnam0899/esi-contracts` and `@dtnam0899/dsl-schema`, runs NSwag 14.7.1 from the tool manifest, writes the core-api DTOs `src/Esi.Core.Api/Contracts/CoreApi.g.cs` + `CONTRACT_VERSION`, the agents-api client `src/Esi.Core.Infrastructure/Agents/AgentsApi.g.cs`, the A2UI catalog `src/Esi.Core.Infrastructure/Dsl/Schema/` and the shared DSL fixtures `tests/Esi.Core.UnitTests/Fixtures/dsl-schema/`, each with its source recorded). Commit the result in the same PR; never edit these files.
- Add a migration: `dotnet tool restore && dotnet ef migrations add <Name> --project src/Esi.Core.Infrastructure --startup-project src/Esi.Core.Infrastructure --output-dir Persistence/Migrations`
- Apply migrations: `dotnet ef database update --project src/Esi.Core.Infrastructure --startup-project src/Esi.Core.Infrastructure` (locally); in containers the `migrate` compose service runs the EF Core migrations bundle.
- Docker: `docker build --target test .` (format, build, unit tests; also the pre-commit command in `.esi-test-cmd`), `docker build -t esi-core:<version> --build-arg VERSION=<version> .` (runtime, non-root, `HEALTHCHECK` on `/health`).
- Compose (settings from the shell or a git-ignored `.env`, see `.env.example`; without them local-only passwords are used): `docker compose up` (Postgres, SQL Server with `esi_customer`, migrations, API on http://localhost:8080), `docker compose --profile integration run --rm integration-tests` (integration tests). Build context is this directory only.
- Two database containers, ports published on 127.0.0.1 only (`ESI_CORE_PG_PORT` 5432, `ESI_CORE_SQL_PORT` 1433): `postgres` (`postgres:17.10-alpine`, user `esi`, password `ESI_CORE_PG_PASSWORD`) holds the app database `esi_core`; `sqlserver` (memory capped by `ESI_CORE_SQL_MEMORY_LIMIT_MB`, default 2048) holds the users' side: `esi_customer`, a sample customer database for manual testing, and `esi_target` (recreated by the integration tests). `docker compose up -d postgres customer-db-seed` starts only the databases (then `docker compose run --rm migrate` for the `esi_core` schema). The one-shot `customer-db-seed` (`scripts/seed-customer-db.sh`) creates `esi_customer` from the integration-test sample schema with the read-only login `esi_customer_reader` (password `ESI_CORE_CUSTOMER_READER_PASSWORD`), then loads `scripts/customer-db-extra-data.sql` once (also into an existing `esi_customer`): `dbo.Categories`, `hr.Employees` (self-referencing manager), `dbo.Payments`, extra columns, and about 60 customers, 32 products, 1,500 orders (2025-01 to 2026-10) with deterministic values. It never changes data already there; `docker compose down -v` resets it. Integration tests and `esi_target` never use the extra data. Connection to enter in the portal: `Server=sqlserver;Database=esi_customer;User Id=esi_customer_reader;Password=<reader password>;TrustServerCertificate=True` for the compose api, `Server=localhost,<port>;…` for `dotnet run`.
- SQL Server images are amd64 only and need at least 2000 MB: on Apple silicon enable Rosetta emulation in Docker Desktop (SQL Server fails under QEMU) and give the Docker VM 4 GB or more.

## Structure
- `src/Esi.Core.Api/` - ASP.NET Core host: `Program.cs` (configuration, logging, `/health` liveness and `/health/ready` readiness), `Logging/RedactingJsonConsoleFormatter.cs`, `Endpoints/` (minimal API per contract tag, mapping to the generated DTOs), `Problems/EsiProblemHandler.cs` (problem+json, `urn:esi:problem:<name>`), `Auth/` (`AuthExtensions` mode selection, Oidc JWT bearer + `OidcUserMappingMiddleware` + 401 `UnauthenticatedProblem`, local admin stand-in), `Contracts/` (generated, never edited; `CONTRACT_VERSION` records the pinned contract)
- `src/Esi.Core.Application/` - use cases and application services: `Consent/` (terms as embedded Markdown `Consent/Terms/<version>.md`, acceptance), `Connections/` (`ConnectionService`, and `ConnectionAccess`, the single owner + consent check every connection-using feature must call), `Queries/` (`QueryService`, `ISqlStatementValidator`, `ITargetDatabase`), `Schema/SchemaService`, `Chat/`, `Scripts/`, `Visualizations/` (`VisualizationService`, `IDslValidator`), `Artifacts/`, `Dashboards/`, `Agents/IAgentsClient`, `Security/` (`SecretValue`, `ISecretProtector`), `Problems/EsiProblem`; `Logging/SensitiveDataRedactor.cs` masks secrets in log text
- `src/Esi.Core.Domain/` - domain model (`Connections/Connection`, `EncryptedSecret`, `Consent/ConsentAcceptance`, `Schema/`, `Chat/ChatSession`, `ChatMessage`, `Scripts/Script`, `Artifacts/Artifact`, `Dashboards/Dashboard`, `DashboardItem`); no framework or database dependencies
- `src/Esi.Core.Infrastructure/` - EF Core `AppDbContext`, entity configurations, repositories, design-time factory, `Persistence/Migrations/`; `Security/` (`MasterKeyRing`, `AesGcmSecretProtector`); `Connections/` (connection string inspector, `SqlConnectionProbe`); `Queries/` (`SelectStatementValidator`, `SqlTargetDatabase`); `Agents/` (generated client + `HttpAgentsClient`); `Dsl/` (`DslValidator`, vendored `Schema/`); `DependencyInjection.AddInfrastructure`
- `tests/Esi.Core.UnitTests/` - unit tests and in-memory API tests (`WebApplicationFactory`, no database)
- `tests/Esi.Core.IntegrationTests/` - tests against the compose databases: `esi_core` on Postgres and `esi_target` on SQL Server (fail, not skip, without `ESI_CORE_TEST_APPDB` / `ESI_CORE_TEST_TARGETDB`)

## Project context
- Configuration: environment variables only (`ESI_CORE_` prefix, `__` for sections, e.g. `ESI_CORE_AppDb__ConnectionString` (an Npgsql connection string), `ESI_CORE_Logging__LogLevel__Default`) and `dotnet user-secrets` (`UserSecretsId` `esi-core-backend`) in Development; appsettings files are not loaded. The API fails at startup if the app database connection string is missing.
- Never commit connection strings, passwords, signing keys or client secrets; `.env` is git-ignored.
- Authentication (ADR-0006, ESI-86): `ESI_CORE_Auth__Mode` is required; any other value refuses to start. `Oidc`: JWT bearer tokens (RS256) validated against `ESI_CORE_Auth__Authority` (issuer URL with the trailing slash, e.g. `https://<tenant>.auth0.com/`; keys from its discovery document) and `ESI_CORE_Auth__Audience`; a fallback policy requires an authenticated user on every endpoint except `/health` and `/health/ready`; a missing or invalid token is 401 problem+json `unauthenticated`. `OidcUserMappingMiddleware` maps the token's (`iss`, `sub`) to the internal id in the `Users` table (created on first request, unique on issuer + subject, concurrent first requests resolve to one row); `ICurrentUser.UserId` is that id and no provider id is stored elsewhere. `LocalAdmin`: every request acts as one local admin (`ESI_CORE_Auth__LocalUserId`, default `00000000-0000-0000-0000-000000000001`), allowed only with `ASPNETCORE_ENVIRONMENT=Development` (compose, the test hosts and `infra/e2e` set it). Test hosts set `ESI_CORE_*` variables only inside their locked `CreateHost` (`TestEnvironment.CreateHost`, `CoreApiFactory.CreateHostWith`) because hosts build in parallel; Oidc tests sign tokens locally (`tests/Esi.Core.UnitTests/TestTokens.cs`, linked into the integration tests). Integration tests replace the agent with `FakeAgents` and switch users with a test-only `X-Test-User` header registered in the test host, not in the application. Tests that use `esi_target` share the `target-database` xUnit collection (one seeded database, run one class at a time).
- Connection strings (ADR-0003): envelope encryption with AES-256-GCM; master keys from `ESI_CORE_Encryption__MasterKeys__<version>` (base64, 32 bytes) and `ESI_CORE_Encryption__ActiveKeyVersion`; the API fails at startup without a valid active key. Associated data binds each secret to its connection and owner. Plaintext exists only as `SecretValue` inside a call (`ToString` prints `***`); responses use generated DTOs that have no secret field; connection test failures map SQL Server error numbers to fixed messages. compose and tests use dummy keys only. Losing the master key makes stored connections unrecoverable.
- Consent (SR-1): users accept the current terms version before adding a connection; a new terms version (new embedded file + `EmbeddedConsentTermsProvider.CurrentVersion`) requires accepting again. Withdrawn consent: operations that use the connection answer 403 `consent-withdrawn`; listing, reading, granting again and deleting still work. Other users' connections answer 404 on every operation.
- SQL execution (ADR-0004, ESI-16): `SelectStatementValidator` parses with ScriptDom 180.140.0 (`TSql170Parser`) and accepts one batch with one plain SELECT whose every syntax node is on `AllowedNodes` and every function on `AllowedFunctions` (system functions only); unknown nodes are rejected by default. Adding a construct needs a corpus test in `SelectStatementValidatorTests` plus the allow-list entry. Before running, referenced objects must be user tables (`sys.all_objects` type `U`, not shipped by Microsoft): views, table-valued functions, synonyms and system objects are rejected; cross-database and linked-server names are rejected by the validator. `SqlTargetDatabase` runs with `ApplicationIntent=ReadOnly` inside a transaction that is always rolled back, timeout `ESI_CORE_Execution__CommandTimeoutSeconds` (default 30, timeout = 504 `execution-timeout`), streams the reader to return 20 rows and count the rest (stateless pages re-run the statement), truncates cells at 65,536 characters, and requires unique, non-empty column names. Every attempt is logged by `QueryService` (user, connection, outcome, duration, statement with literals as `?` and comments removed, SHA-256 of the original); results and the original text are never logged. Users should still connect with a read-only database login (stated in the consent terms; the portal shows it with ESI-19).
- Chat and scripts (SR-2, SR-3, ESI-17): `ChatService` reads the schema, sends the question, the last 20 messages and the schema structure to the agent (`IAgentsClient`, generated agents-api client over HTTP, `ESI_CORE_Agents__BaseUrl`, timeout `ESI_CORE_Agents__TimeoutSeconds`, default 120) and stores both messages; nothing is executed. A `stored-procedure` answer is saved to the script library. Agent failures (unreachable, no model, timeout, 5xx) are 503 `agents-unavailable` and store nothing. Sessions and scripts are owner-scoped (404) and hidden while consent is withdrawn (403); a script can always be deleted.
- Visualizations (SR-5): only column definitions and the intent (`table`, `kpi`, `chart`) go to the agent, with the basic catalog id for tables and KPIs and the ESI catalog id for charts (ADR-0009). Core validates every candidate with `DslValidator` (port of `@dtnam0899/dsl-core` 0.2.0: envelope, component schemas of the document's catalog via JsonSchema.Net 9.4.0 from the vendored `catalog.json` and `esi-catalog.json`, ESI rules, and on the ESI catalog the chart rules `chart-column-type` / `chart-series`) and retries with the findings at most `ESI_CORE_Visualization__MaxRetries` (default 2) times; then 422 `dsl-validation-failed` with `issues`. Chart rules need DSL column types: `DslColumnTypes.FromSqlType` maps SQL Server types exactly like the portal's `toColumnType` (keep them in step). Forms are 422 `visualization-not-supported`. `DslValidatorTests` must keep passing the shared dsl-schema fixtures (same codes as dsl-core); the stored `DslDocument` uses `protocolVersion` `v0.9` and `dslSchemaVersion` = the dsl-schema package version (`0.1.0` or `0.2.0`; a chart document needs `0.2.0`). Charts can be saved as artifacts since core-api 0.4.0 (ESI-119, see Artifacts and dashboards).
- Artifacts and dashboards (SR-7, SR-8): saving an artifact validates its SELECT (`SelectStatementValidator`) and its DSL against the expected columns (`DslValidator`), then stores the DSL JSON, `dslSchemaVersion`, the SELECT and the columns (no rows, no secrets). `kind` (`table`, `kpi`, `chart`) must match the DSL (ADR-0010): `chart` exactly for an ESI-catalog document, otherwise 400 on `kind`. The response `kind` is an open set in the contract (generated as `string`); `ArtifactEndpoints.Kind` maps each domain kind explicitly and throws on an unknown one, so never add a fallback branch. `executeArtifact` runs the saved SELECT through `QueryService` (same policy, timeout and 20-row paging). Dashboards store item layout (x, y, width, height) with the dashboard, never in the DSL, and return artifacts without data so each item loads on its own; items are ordered by grid position. Status rules: withdrawn consent or outdated terms hide artifacts and dashboards (403); a deleted connection shows `connection-unavailable` and `executeArtifact` answers 409 `artifact-unavailable`; a deleted artifact leaves a `missing` item; a `dslSchemaVersion` the validator does not support is `migration-required`. No foreign keys from artifacts to connections or from items to artifacts, on purpose.
- Contract DTOs: generated with NSwag (DTOs only, System.Text.Json; the script maps enum strings with `JsonStringEnumMemberName`); endpoints are written by hand and must match the pinned contract version.
- Logging: JSON lines on stdout through `RedactingJsonConsoleFormatter`; messages, state values and exceptions pass through `SensitiveDataRedactor`. Add new secret key names there rather than bypassing it (ADR-0003 requires that no log contains a secret).
- `esi_target` stands in for a user's target database; never point the app database at it.
- Test data (P0-14, `docs/process/test-data.md`): integration tests recreate `esi_target` from `tests/Esi.Core.IntegrationTests/Fixtures/target-sample-schema.sql` (customers/products/orders with foreign keys and rows, the view `dbo.vw_CustomerRevenue`, plus `dbo.usp_GetCustomerOrders`, whose definition tests read and nothing executes). Change the schema there; other projects never read it.
- Security-sensitive areas that need a human reviewer: `SensitiveDataRedactor`, `AesGcmSecretProtector`/`MasterKeyRing` and connection handling (ESI-15), the consent text (`Consent/Terms/*.md`, AI-drafted, needs admin/legal approval before production), SQL execution (ESI-16), and authentication (`Auth/`, `Users` mapping).
