# Changelog

All notable changes are generated from Conventional Commits by the release flow. Do not edit released sections by hand.

## Unreleased

- Charts as artifacts (ADR-0010, ESI-119, core-api 0.4.0): `createArtifact` accepts `kind` `chart` (new `ArtifactKind.Chart`, stored as the string `Chart`, no migration) and answers 400 `invalid-request` on `kind` when it does not match the DSL (`chart` = ESI catalog, `table`/`kpi` = basic catalog). Artifact and dashboard responses return `chart`. Kind mappings between the contract and the domain are explicit switches; an unknown domain kind throws instead of being returned as a table (it used to fall back to `table`).
- Pinned contract `@dtnam0899/esi-contracts` 0.4.0: `ArtifactSummary.kind` is an open set (`x-extensible-enum`), so NSwag generates it as `string`; `CreateArtifactRequestKind` gains `Chart`.
- Chart visualizations (ADR-0009, ESI-114, core-api 0.3.0): `createVisualization` accepts `intent.kind` `chart` and asks agents for DSL on the ESI catalog (`dtnam0899.github.io:esi-catalog-v0_9-1`); tables and KPIs keep the basic catalog. `DslValidator` ports dsl-core 0.2.0: both catalogs, `EsiChart`, the chart rules `chart-column-type` and `chart-series` (column types are mapped from the SQL types like the portal does, `DslColumnTypes`), and all `@dtnam0899/dsl-schema` 0.2.0 fixtures. A chart document must name dsl-schema 0.2.0. A `kind` the contract does not name is refused instead of being sent as a table. Saving a chart as an artifact is not possible yet (core-api artifact `kind` is `table | kpi`; ESI-119).
- Pinned contract `@dtnam0899/esi-contracts` 0.3.0 and `@dtnam0899/dsl-schema` 0.2.0; `scripts/sync-published.sh` also vendors the ESI catalog (`Dsl/Schema/esi-catalog.json`).
- Pinned contract `@dtnam0899/esi-contracts` 0.2.0 (bearer security scheme, 401 `unauthenticated`, 503 `agents-unavailable`); the generated DTOs and agents-api client are unchanged apart from their source header.
- Oidc authentication (ADR-0006, ESI-86, core-api 0.2.0): `ESI_CORE_Auth__Mode=Oidc` validates JWT bearer tokens (RS256) from `ESI_CORE_Auth__Authority` for `ESI_CORE_Auth__Audience`; every endpoint except `/health` and `/health/ready` requires an authenticated user; missing or invalid tokens answer 401 `unauthenticated` (problem+json). New `Users` table (migration `AddUsers`) maps (issuer, subject) to the internal user id, created on the first request. `Authorization` values are masked in logs. BREAKING CHANGE: `LocalAdmin` starts only with `ASPNETCORE_ENVIRONMENT=Development`.
- App database on PostgreSQL (ADR-0008, ESI-94): EF Core uses the Npgsql provider and `ESI_CORE_AppDb__ConnectionString` takes an Npgsql connection string; migrations reset to one `InitialCreate`; compose adds a `postgres` service for `esi_core`, and `sqlserver` holds only the `esi_target` test database. Users' target databases stay SQL Server. A chat answer is stored 1 µs after its question (was 1 tick) so the order survives Postgres' microsecond precision. BREAKING CHANGE for deployments: an existing SQL Server app database is not migrated.

## 0.1.0

- Artifacts and dashboards (ESI-17 part 2, core-api 0.1.0): saved artifacts with SQL and DSL validation and live `executeArtifact`, dashboards with items and persisted layout, consent hiding, `connection-unavailable` / `missing` / `migration-required` states instead of stale data.
- Chat, scripts and visualizations (ESI-17 part 1, core-api 0.1.0): chat sessions with synchronous SQL generation through services/ai-agents (generated agents-api client), automatic script library for stored-procedure answers, visualizations validated by a .NET port of dsl-core against the shared dsl-schema fixtures with up to 2 retries, `agents-unavailable` (503). `scripts/sync-published.sh` replaces `generate-contracts.sh` and also vendors the A2UI catalog and DSL fixtures from `@dtnam0899/dsl-schema` 0.1.0.
- Schema discovery and read-only SQL execution (ESI-16, core-api 0.1.0 `getConnectionSchema`, `executeQuery`): schema metadata (tables, views, columns, keys, procedure definitions as text); ScriptDom allow-list validation of a single SELECT (ADR-0004) with a bypass corpus; user tables only; read-only intent in an always rolled-back transaction; configurable timeout; 20-row stateless pages with remaining count; 64 KB cell cap; inline execution log with masked literals and hash.
- Connections and consent (ESI-15, core-api 0.1.0): consent terms (AI-drafted draft `2026-10-18.1`) and acceptance, per-connection grant/withdraw, connections create/list/get/update/delete/test with envelope encryption (AES-256-GCM, versioned master keys, rotation re-wrap), owner isolation (404) and consent checks for every operation, problem+json errors, local admin stand-in that must be enabled explicitly, contract DTOs generated with NSwag from `@dtnam0899/esi-contracts` 0.1.0, migration `AddConnectionsAndConsent`.
- Scaffold: .NET 10 solution (`Api`, `Application`, `Domain`, `Infrastructure`, unit and integration tests), `/health` liveness and `/health/ready` app-database readiness, environment-only configuration with user-secrets for local use, JSON console logging with secret redaction, EF Core `AppDbContext` with an initial migration and a migrations bundle, multi-stage Dockerfile (non-root, `HEALTHCHECK`, locked restore) and compose file with one SQL Server holding the app database and a separate target database for integration tests.
