# Changelog

All notable changes are generated from Conventional Commits by the release flow. Do not edit released sections by hand.

## 0.1.0

- Artifacts and dashboards (ESI-17 part 2, core-api 0.1.0): saved artifacts with SQL and DSL validation and live `executeArtifact`, dashboards with items and persisted layout, consent hiding, `connection-unavailable` / `missing` / `migration-required` states instead of stale data.
- Chat, scripts and visualizations (ESI-17 part 1, core-api 0.1.0): chat sessions with synchronous SQL generation through services/ai-agents (generated agents-api client), automatic script library for stored-procedure answers, visualizations validated by a .NET port of dsl-core against the shared dsl-schema fixtures with up to 2 retries, `agents-unavailable` (503). `scripts/sync-published.sh` replaces `generate-contracts.sh` and also vendors the A2UI catalog and DSL fixtures from `@dtnam0899/dsl-schema` 0.1.0.
- Schema discovery and read-only SQL execution (ESI-16, core-api 0.1.0 `getConnectionSchema`, `executeQuery`): schema metadata (tables, views, columns, keys, procedure definitions as text); ScriptDom allow-list validation of a single SELECT (ADR-0004) with a bypass corpus; user tables only; read-only intent in an always rolled-back transaction; configurable timeout; 20-row stateless pages with remaining count; 64 KB cell cap; inline execution log with masked literals and hash.
- Connections and consent (ESI-15, core-api 0.1.0): consent terms (AI-drafted draft `2026-10-18.1`) and acceptance, per-connection grant/withdraw, connections create/list/get/update/delete/test with envelope encryption (AES-256-GCM, versioned master keys, rotation re-wrap), owner isolation (404) and consent checks for every operation, problem+json errors, local admin stand-in that must be enabled explicitly, contract DTOs generated with NSwag from `@dtnam0899/esi-contracts` 0.1.0, migration `AddConnectionsAndConsent`.
- Scaffold: .NET 10 solution (`Api`, `Application`, `Domain`, `Infrastructure`, unit and integration tests), `/health` liveness and `/health/ready` app-database readiness, environment-only configuration with user-secrets for local use, JSON console logging with secret redaction, EF Core `AppDbContext` with an initial migration and a migrations bundle, multi-stage Dockerfile (non-root, `HEALTHCHECK`, locked restore) and compose file with one SQL Server holding the app database and a separate target database for integration tests.
